3. Робота з гілками та Git rebase
----------------------------------------------------------------------

Мета: показати, як працює rebase, коли є кілька гілок із власними комітами.

3.1. Створення гілки feature_1

Перемикаємося від master (або main) на нову гілку:

git checkout -b feature_1

Робимо декілька змін у файлі notes.txt:

echo "Зміна 1 в feature_1" >> notes.txt
git add notes.txt
git commit -m "feature_1: change 1"

echo "Зміна 2 в feature_1" >> notes.txt
git add notes.txt
git commit -m "feature_1: change 2"

3.2. (За методичкою) створюється також гілка feature_2 від master,
в якій робиться окрема зміна. Після цього для демонстрації використовується:

git checkout feature_1
git rebase feature_2

Суть rebase:
- Git бере унікальні коміти гілки feature_1;
- відтворює їх поверх останнього коміту в feature_2;
- в результаті історія стає лінійною, але хеші комітів змінюються.

Перегляд історії:

git log --oneline --graph --all

4. Інтерактивний rebase і squash комітів
----------------------------------------------------------------------

Мета: об’єднати кілька дрібних комітів в один (squash).

4.1. Створення кількох комітів (приклад на гілці feature_1)

Виконується кілька змін:

echo "squash: step 1" >> notes.txt
git add notes.txt
git commit -m "squash: step 1"

echo "squash: step 2" >> notes.txt
git add notes.txt
git commit -m "squash: step 2"

echo "squash: step 3" >> notes.txt
git add notes.txt
git commit -m "squash: step 3"

Перегляд історії:

git log --oneline --graph

4.2. Інтерактивний rebase для об’єднання трьох останніх комітів

Запускаємо:

git rebase -i HEAD~3

Відкривається список останніх трьох комітів:

pick <hash1> squash: step 1
pick <hash2> squash: step 2
pick <hash3> squash: step 3

Змінюємо на:

pick   <hash1> squash: step 1
squash <hash2> squash: step 2
squash <hash3> squash: step 3

Після збереження та закриття редактора Git запропонує об’єднати повідомлення комітів.
Можна залишити, наприклад:

squash: combined steps 1–3

В результаті три коміти перетворюються на один із новим хешем. Це видно за допомогою:

git log --oneline --graph

5. Git stash – тимчасове збереження змін
----------------------------------------------------------------------

Мета: показати, як тимчасово відкласти незакомічені зміни.

5.1. Створення незакомічених змін

Переконуємось, що ми на master (або потрібній гілці):

git checkout master

Робимо зміни:

echo "Тимчасова зміна перед stash" >> notes.txt
echo "Ще одна тимчасова зміна" > temp_file.txt

Перевірка:

git status

5.2. Збереження змін у stash

git stash

Робочий каталог знову чистий:

git status

5.3. Перегляд списка stash та відновлення змін

git stash list
git stash pop

Після pop зміни повертаються в робочу директорію, файли знову відображаються як змінені:

git status
type notes.txt
type temp_file.txt

----------------------------------------------------------------------

Мета: позначити певний стан репозиторію міткою (наприклад, версією релізу).

6.1. Створення тегу

git checkout master
git tag v1.0.0

Перегляд дійсних тегів:

git tag

6.2. Видалення тегу

git tag -d v1.0.0

Перевірка:

git tag

7. Git patch – створення та застосування патчів
----------------------------------------------------------------------

Мета: показати, як передавати окремі зміни у вигляді файлу-патчу.

7.1. Коміт для демонстрації патча

echo "Зміна для патча" >> notes.txt
git add notes.txt
git commit -m "Change notes for patch demo"

7.2. Створення патча для останнього коміту

git format-patch HEAD^ 

У каталозі з’явиться файл:
0001-Change-notes-for-patch-demo.patch

7.3. Відкат до попереднього стану та застосування патча

git reset --hard HEAD^

Після цього commit “Change notes for patch demo” зникає з історії.

Далі застосовуємо патч:

git apply 0001-Change-notes-for-patch-demo.patch
git status
git add notes.txt
git commit -m "Apply patch for notes change"

Таким чином зміни з патча знову потрапляють у репозиторій як окремий коміт.

8. Git hooks – створення власного hook’а commit-msg
----------------------------------------------------------------------

Мета: навчитись використовувати hook-скрипти, що автоматично виконуються при певних діях Git.

Завдання: реалізувати hook, який забороняє коміт, якщо повідомлення коміту коротше 10 символів.

8.1. Створення файлу hook’а commit-msg

У каталозі репозиторію:

відкриваємо файл .git/hooks/commit-msg (створюємо, якщо його немає):

(у Windows можна використати, наприклад, команду)
notepad .git/hooks/commit-msg

Вставляємо такий вміст:

#!/bin/sh

MSG_FILE="$1"
MSG=$(tr -d '\r\n' < "$MSG_FILE")
LEN=${#MSG}

if [ "$LEN" -lt 10 ]; then
  echo "ERROR: Commit message must be at least 10 characters long." >&2
  exit 1
fi

exit 0

(У Git Bash можна зробити файл виконуваним:
chmod +x .git/hooks/commit-msg)

8.2. Перевірка роботи hook’а

Робимо якусь зміну:

echo "Test hook" >> notes.txt
git add notes.txt

Спроба зробити коміт із надто коротким повідомленням:

git commit -m "short"

Очікувано: hook виведе помилку та не дасть зробити коміт.

Спроба з коректним повідомленням:

git commit -m "Commit with valid message"

Цей коміт має пройти успішно.

----------------------------------------------------------------------
9. Додаткові команди: merge vs rebase, cherry-pick, reflog
----------------------------------------------------------------------

9.1. Порівняння merge та rebase

- git merge:
  - об’єднує історію двох гілок,
  - створює merge-коміт,
  - історія зберігає розгалуження.

- git rebase:
  - “переграє” коміти гілки поверх іншої,
  - не створює merge-коміту, історія стає лінійною,
  - змінює хеші комітів (небезпечно робити на публічних гілках).

9.2. Git cherry-pick

Команда дозволяє взяти один конкретний коміт з іншої гілки
та застосувати його в поточній:

git cherry-pick <hash_коміту>

У результаті з’являється новий коміт з тими ж змінами, але новим хешем.

9.3. Git reflog

Команда:

git reflog

показує історію переміщень HEAD (коміти, checkout, reset тощо) та допомагає відновлювати “втрачені” коміти. Наприклад, якщо зроблено помилковий reset, можна знайти старий хеш у reflog і повернутись:

git reset --hard <старий_hash_з_reflog>
